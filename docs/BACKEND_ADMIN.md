# Backend и администрирование

## Контракт данных

- Неизвестная цена: `price_min=null`, `price_max=null`, `is_free=false`.
  Бесплатный вход: обе цены `0`, `is_free=true`. Диапазон `0–500` не означает
  бесплатное мероприятие. При известной только верхней границе сохраняется
  `price_min=null`; поиск по бюджету использует известную границу.
- `EventRecord.sources` содержит все источники из `event_sources`.
  Прежние поля `source_url/source_type/source_hash/verified_at` сохранены и относятся
  к основному источнику. Повтор одного источника не создаёт новую строку.
- Канонические статусы: `published`, `draft`, `cancelled`. Импорт, CLI и сервис
  модерации также принимают `опубликовано`, `черновик`, `отменено`.
  Поиск показывает только `published`. Прямая карточка отменённого события доступна;
  черновик доступен только доверенному вызову `include_drafts=True` и администратору бота.
- `update_event_status()` устанавливает `status_locked`: повторный импорт,
  стартовая загрузка и reprocess не отменяют решение модератора.
- Дедупликация использует нормализованные название, город, площадку и время начала
  с точностью до минуты. Переданный извне `dedup_key` не используется.
  Старые дубли сохраняются как архивные строки с `merged_into`; старые ID ведут
  к основной карточке. Для актуальных строк действует уникальный индекс.
  Источники и связанные заявки переносятся; при конфликте статусов выбирается
  `cancelled`, затем `draft`, затем `published`.

## Заявки и аудит

`FeedbackService.submit(message, event_id=None, actor=...)` создаёт заявку `pending`.
Отсутствующий `event_id` означает предложение нового события.
`list_requests(status=None, limit=50, offset=0)` возвращает очередь;
`update_status(id, status, actor=...)` принимает `pending`, `in_progress`,
`resolved`, `rejected`. Обработка заявки сама по себе не меняет событие.

Существующий `audit_log` фиксирует создание/обновление событий, источников,
объединение, модерацию, создание и обработку заявок, а также перенос данных
миграцией. Сохраняются инициатор, UTC-время, действие и изменения.
Запись события/источников/аудита атомарна. При ошибке аудита изменения откатываются.
Импорт сериализует определение идентичности в PostgreSQL блокировкой таблицы,
в SQLite — `BEGIN IMMEDIATE`; это простой вариант для текущего объёма каталога.

## FastAPI

REST-приложение запускается после отдельной подготовки БД:

```sh
python -m src.bootstrap prepare --seed-demo
uvicorn src.api:create_app --factory
```

- `GET /events`: поиск, фильтры и пагинация; ответ `events`, `total`, `explanation`.
- `GET /events/{id}`: публичная карточка без внутренних полей дедупликации и сырых данных.
- `POST /feedback`: тело `{"event_id": null, "message": "Предлагаем событие…"}`.
  Инициатор публичной заявки фиксируется сервером как `api:anonymous`.
- `/docs`: описание параметров и nullable-полей.

Административные маршруты `/api/v1/admin/*` требуют отзывную сессию в БД; операции записи также требуют CSRF-токен и допустимый Origin. Роль `moderator` управляет карточками и заявками, роль `admin` дополнительно импортирует данные и читает журнал. Административные ответы всегда имеют `Cache-Control: no-store`. API и бот не применяют миграции при старте. Для входа достаточно `ADMIN_PASSWORD` в локальном `.env`; отдельный `ADMIN_SECRET` необязателен, поскольку сессии используют `RATE_LIMIT_SECRET`.

## Миграции

`001_initial_schema.sql` задаёт исходную схему. `002_admin_backend.sql` переносит старые данные, источники и цены. `003_security_search.sql` добавляет сессии, общие лимиты запросов и нормализованные поля поиска. Миграции запускаются только командой `python -m src.bootstrap prepare` или сервисом Compose `prepare`. После миграций `prepare` создаёт отдельные роли PostgreSQL для API, бота и очистки данных; их пароли задаются переменными `API_DB_PASSWORD`, `BOT_DB_PASSWORD`, `MAINTENANCE_DB_PASSWORD`.

PostgreSQL изменяет колонки через `ALTER TABLE`; SQLite копирует таблицу и
воссоздаёт индексы/триггеры в одной транзакции. Версия миграции записывается
в той же транзакции. Прерывание оставляет прежнюю схему и данные.
Переносятся прежние источники; дополнительные восстанавливаются из `raw_events`,
если их удалось сопоставить с существующим событием.

Ошибочно обнулённые цены восстанавливаются по сырому payload. Если исходные данные
отсутствуют или повреждены, старое `0/is_free=true` нельзя надёжно отличить от
настоящего бесплатного входа: оно сохраняется и требует ручной проверки.
Проверяйте миграции сначала на отдельной БД.

## Проверка

```sh
python -m pip install -r requirements-dev.txt
python -m pytest -q
TEST_POSTGRES_URL=postgresql://user@localhost:5432/test_db python -m pytest -q
```

Без `TEST_POSTGRES_URL` PostgreSQL-проверки явно пропускаются. При его наличии
каждый тест создаёт собственную схему `test_<uuid>` и удаляет только её после
проверки. Используйте отдельную тестовую БД с правом создания схем.
Проверяются SQLite в памяти/файле, PostgreSQL, чистая и старая схема, откат миграции,
цены, источники, повторный/конкурентный импорт, API, бот, CLI, заявки и аудит.

Проверки безопасности дополнены тестами кеширования, авторизации, лимитов, импорта и сроков хранения.

## REST Level 2

Новые GET: `/health`, `/api/v1/events`, `/api/v1/events/{event_id}`,
`/api/v1/cities`, `/api/v1/categories`, `/api/v1/venues`.
Старые `/events`, `/events/{event_id}`, `/feedback` сохранены.
Справочники отражают опубликованный каталог; categories и venues принимают `city`.
Health проверяет доступность БД (`SELECT 1`), при ошибке возвращает 500.

Список v1 принимает `page` (от 1), `page_size` (1–100), возвращает
`events/total/pages/page/page_size/explanation`; пустая выборка имеет `pages=0`.
Старый список сохраняет `limit/offset`. Оба поддерживают
`sort=date_asc|date_desc|price_asc`; неизвестные цены в конце ценовой сортировки.
Фильтры: `query_text`, `city`, `category`, `venue`, `date_from/date_to`,
`max_price`, `is_free_only`, `max_age_limit`, `time_after/time_before`,
`max_duration_min`, `language`, `tag`.
Даты принимаются в ISO 8601; дата без времени включает весь день.
Часовой пояс явного смещения приводится к местному времени Башкортостана (UTC+5).
Обратный период, неверные даты/время и недопустимые параметры возвращают 422.
Фильтрация, сортировка и пагинация выполняются в SQL по нормализованным полям и индексам.

Ошибки имеют `error: {code, message, details}`, `request_id` и совместимое строковое
`detail`. Сообщения русскоязычные; 500 не раскрывает текст внутреннего исключения.
OpenAPI 3.1 описывает ответы и ошибки, `/docs` сохранён.

Настройки: `CORS_ORIGINS` — origins через запятую (по умолчанию пусто),
`PUBLIC_CACHE_MAX_AGE` — секунды (по умолчанию 60).
Успешные GET каталога возвращают `Cache-Control: public, max-age=N, must-revalidate`;
health, административные ответы, ошибки и изменения — `no-store`. ETag не реализован.
HTTP-обработчик генерирует `X-Request-ID` и использует существующий structured logger.
