# Краткая записка о решении (Раздел 12 ТЗ)

## 0. Текущий статус

Проект подготовлен к сдаче на **Уровень 3 («Агент»)**: каталог и модерация, веб/API-контур, агентный диалог в Telegram и на сайте. Контрольные метрики внутреннего набора измерены; внешние 10 запросов и ручная проверка утверждений ещё нужны для итогового коэффициента качества.

Telegram-бот открывает компактное меню сразу по `/start`. Пресеты показывают события одним нажатием, кнопка карточки — вторым; свободный текст запускает поиск без анкеты и мастера досуга. Язык и геолокация настраиваются по желанию на одном экране.

Архитектура агента — **Jev (1.5B) + Light/Heavy (3B) + Deterministic Fallback**. Jev выбирает маршрут по признакам запроса; модели могут предлагать только разрешённые инструменты. Бэкенд валидирует аргументы и формирует карточки из записей БД. Подписка и обратная связь требуют подтверждения. Отказ модели переводит поиск в детерминированный режим.

По разделу 9.1 внутренний замер: заполненность 100 %, дубли 0 %, полнота 100 %, ложная пустая выдача 0 %, p95 0,0024 с, импорт 100 событий 100 % (см. README). По разделу 9.2 внутренний прогон `python -m src.cli agent-metrics` в `AI_MODE=no-ai` при опорной дате 2026-11-13: 66 запросов, 13 инъекционных кейсов, 0 выдуманных карточек, 100 % структурно сверенных по БД карточек, 100 % проверяемых ограничений, уточнений, честных отказов и вызовов инструментов, p95 0,008 с, 0 показов отменённых как актуальных, 20/20 последовательных запросов. Отдельная десятка `--holdout` составлена командой и не является независимыми внешними запросами. ТЗ содержит 12 метрик; № 10 нормируется только для уровня 4. Структурная сверка карточек не измеряет фактическую точность всего текста. Ручная проверка утверждений и независимая внешняя десятка не проведены.

Итоговая схема объединена в одну атомарную базовую миграцию для чистых PostgreSQL и SQLite; столбца `phone` в ней нет. Старую заполненную БД нельзя обновлять этой миграцией. `scripts/check_legacy_upgrade.py` даёт только читающий preflight; после резервной копии нужен отдельный перенос в новую БД с проверкой ID, источников, статусов и связей. В новой подписке `period` задаёт даты событий и хранится отдельно от `expires_at`; отсутствие периода означает все даты.

Стоимость диалога: **0,00 ₽** по внешним токенам локально. Оценка для API **< 0,15 ₽** при пороге **≤ 5 ₽**; формула: сумма входных и выходных токенов по ценам за миллион, умноженная на курс USD/RUB. Фактический API-замер требует настроенных цен и курса.

### Гибридные рекомендации и CSP-маршрут

`RecommendationService` работает без новых ML-зависимостей. Просмотры `event_views` связываются с Telegram и веб-пользователем через `user_identities`; подписки и добровольно заданные предпочтения дополняют профиль. Скор объединяет косинусную близость символьных 3-грамм, предпочтения, гео-затухание Хаверсина, цену и близость даты. Жадный MMR (`λ = 0,75`) снижает повторение категорий, тегов и площадок. Причины формируются детерминированно. Для холодного старта вес истории переносится на дату; несуществующие, отменённые и объединённые карточки не попадают в подборку.

Планировщик «Выходной день» перебирает совместимые цепочки из 2–4 опубликованных событий через динамическое программирование с отсечением доминируемых по цене и времени состояний. Короткий `date_end` задаёт окончание посещения; многодневный интервал выставки считается периодом доступности, поэтому длительность остановки берётся из `duration_min` или по умолчанию 90 минут. Переезд оценивается через координаты площадок (коэффициент сети 1,3, 24 км/ч), а между событиями обязателен запас 15 минут. При невозможности запрошенного числа остановок отдельные прогоны находят минимально достаточный бюджет или лимит переезда; частичный маршрут сохраняется. В агенте `search_events` и при необходимости `get_event` подтверждают ID перед показом карточек.

Telegram открывает подборку кнопкой «✨ Для вас» без опроса. REST: публичный `GET /api/v1/recommendations` даёт холодный старт, персональная выдача требует собственной пользовательской cookie; `POST /api/v1/weekend-plan` возвращает расписание и диагностику ограничений. На локальном демо-каталоге медианы прогретого SQLite: 1,9 мс холодная подборка, 2,9 мс персональная, 1,1 мс маршрут. Максимальная задержка и время PostgreSQL требуют отдельного замера в целевой среде.

## 1. Обоснование архитектуры для Уровня 1 («Бот»)

В рамках выполнения **Уровня 1** ключевой задачей является создание надёжного, быстрого и полностью достоверного фундамента работы с данными о культурных мероприятиях Республики Башкортостан и предоставление жителю удобного интерфейса в Telegram.

Принятые архитектурные решения:
1. **Детерминированный разбор запросов и поиск по реляционной БД вместо «чата с LLM поверх сырого текста»**:
   - Каждое утверждение в ответе бота на 100 % опирается на верифицированную запись в таблице `events` и её `source_url`. Выдуманные мероприятия технически исключены.
   - Поисковый парсер (`src/services/normalizer.py`) разбирает естественные русскоязычные конструкции (даты, дни недели, время «после 19:00» / «не позже 20:00», бюджет «до 1000 рублей на двоих», возраст ребёнка, язык мероприятия, опечатки в названиях городов РБ по расстоянию Дамерау — Левенштейна) за `< 2 мс` без внешних сетевых вызовов.
   - При недоступности любых внешних сервисов поиск, фильтрация и карточки работают со 100 % доступностью.
2. **Разделение сырых и нормализованных данных (`raw_events` и `events`)**:
   - Исходная запись сохраняется в неизменном JSON-виде в `raw_events` с хешем `source_hash`.
   - При обновлении правил нормализации (например, добавлении новых синонимов площадок или категорий) команда `reprocess-raw` пересчитывает витрину `events` без повторного сбора или повторной загрузки файлов.
3. **Объяснение пустого результата через поочерёдное ослабление ограничений**:
   - Если запрос пользователя с несколькими фильтрами возвращает 0 событий, `SearchService.explain_empty_result` автоматически проверяет, какое именно условие (цена, дата/время, категория, текстовое уточнение или город) блокирует выдачу, и сообщает пользователю точное количество событий, которые появятся при ослаблении конкретного ограничения.

## 2. Отклонённые альтернативы

- **Хранение событий в памяти или JSON-файлах без реляционной СУБД**: отклонено, так как нарушает раздел 10 ТЗ (требуется реляционная БД с миграциями, идемпотентным импортом, индексами и журналом аудита).
- **Использование только кнопочного пошагового мастера (FSM) с обязательным возвратом в главное меню**: отклонено, так как противоречит разделу 6.2 ТЗ («повторный запрос не требует возврата в меню; свободный текст обрабатывается как поисковый запрос; не более трёх действий до карточки»). В нашем решении инлайн-кнопки и свободный текстовый ввод работают параллельно и бесшовно.
- **Зависимость от платного внешнего LLM API на Уровне 1**: отклонено, так как на первом уровне не требуется генеративный диалог, а отказ внешнего API или исчерпание лимита ключей снижает надёжность при проверке.

## 3. Границы применимости и развитие до уровней 2–4

- Реализация покрывает функциональные сценарии **Уровня 3 («Агент»)**; окончательный коэффициент качества подтверждается внешним набором и ручной проверкой по ТЗ.
- Схема базы данных (`events`, `raw_events`, `cities`, `venues`, `categories`, `subscriptions`, `audit_log`, `import_reports`) используется общими сервисами `SearchService`, `ImportService`, `SubscriptionService` и `AgentService`; HTTP, Telegram и веб-клиент не дублируют бизнес-логику поиска и действий.
